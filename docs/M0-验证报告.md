## 3. 各实验记录

### S1 LibreHardwareMonitorLib（非管理员）

```
Open() = 240 ms
Motherboard  GM5HG0A                     update=0.0ms
Cpu          AMD Ryzen 7 8845H ...       update=4.6ms
  Power      Package                     0.0
  Clock      Cores (Average)             0.0
  Voltage    Core #1 VID                1.5     ← 电压居然有值
  Temperature Core (Tctl/Tdie)          0.0     ← 温度是 0，不是 null
summary: temperature=1, fan=0
```

**发现 1（重要）**：驱动未加载时，LHM 不返回 `null`，而是返回 **0.0**。
如果不加判断，UI 会显示"CPU 0 ℃"——比显示 `--` 更糟，属于误导性数据。

**对策**：Provider 层对温度/功耗/频率做"有效值判定"（`<= 0` 或超出物理范围即视为 `Unavailable`），并增加"驱动可用性"探测（管理员 + 至少一个非零温度样本）。这条要写进 §4.11 的验收用例。

**发现 2**：笔记本/迷你主机的风扇由 EC 接管，LHM 读不到（`fan=0`），与预期一致。

### S2 NVML

```
nvmlInit_v2 = 0
device count = 1
[0] NVIDIA GeForce RTX 4060 Laptop GPU | 59 C | 12.5 W | GPU 40% | MEM 1653/8188 MB
```

非管理员即可读到温度、功耗、利用率、显存，耗时 < 5 ms。**结论：GPU 走 NVML 的决策成立。**

### S3 NVMe 温度

```
PhysicalDrive0: access denied (需要管理员)
PhysicalDrive1..7: IOException (不存在)
```

**发现 3**：`IOCTL_STORAGE_QUERY_PROPERTY` 读取温度在**非管理员**下被拒绝。方案里"NVMe 温度零权限可读"的假设在本机不成立。

**对策**：NVMe 温度归入**增强模式**；兼容模式下该项显示 `--`。若管理员复测仍失败，则作为"尽力而为"项默认隐藏。

### S4 系统指标

```
PdhOpenQuery rc=0x00000000
#1 CPU --% | MEM 47.3% (14.8/31.3 GB) | DISK W 0.00 MB/s | NET ...
#2 CPU 16.7% | ... | DISK W 0.61 MB/s
#3 CPU 24.4% | ... | DISK W 0.39 MB/s
```

- **首样本无效**（PDH 需要两次 Collect 才有速率），与设计一致：第一轮必须丢弃。
- 计数器路径写成 `@"\Processor..."` 时返回 `0xC0000BC0`；正确写法是 `@"\Processor..."`（注意：两处示例在 Markdown 里显示相同，错误写法实际少了开头的反斜杠）。**这是一个真实的踩坑点，已补进开发手册 §9.1。**
- 本机 CPU% 量级与系统负载相符，但未与任务管理器同屏逐点对比，M1 联调时补。

### S5 WPF 自绘

| 场景 | 平均帧 | P95 帧 | 单帧绘制 | 分配 | 工作集 / 私有 |
|---|---|---|---|---|---|
| 连续重绘（240 Hz） | 4.18 ms | 4.83 ms | 0.45–0.47 ms | **18 MB/s** | 147 / 106 MB |
| 收敛即停（1 Hz 数据 + 动画） | 14.4 ms（触发间隔） | 30.6 ms | **0.82 ms** | **1.3 MB/s** | 153 / 106 MB |
| WPF 空窗基线 | — | — | — | — | **124.7 / 87.1 MB** |
| WinForms 空窗基线（对照） | — | — | — | — | **80.2 / 39.6 MB** |

**发现 4**：渲染成本极低（< 1 ms），**"自绘"路线成立**；但连续重绘的分配率高一个数量级，验证了"动画收敛即退订 `CompositionTarget.Rendering`"这条规则的价值。

**发现 5（需决策）**：WPF 空窗基线就有 **87 MB 私有 / 125 MB 工作集**，方案中"工作集 ≤ 60 MB"的目标**不可能达成**。WinForms 基线为 39.6 / 80.2 MB。

## 4. Go / No-Go 结论

**条件 Go（继续 M1）**，但有三个决策点必须先拍板：

| # | 决策点 | 建议 |
|---|---|---|
| D1 | 内存预算 | 保留 WPF，把目标改为 **私有 ≤ 110 MB / 工作集 ≤ 150 MB**；若 60–80 MB 是硬指标，改用 **WinForms + 自绘**（视觉与 DPI 能力下降） |
| D2 | 温度的产品口径 | 温度/风扇/功耗/电压/NVMe 全部归入**增强模式（管理员）**；兼容模式只承诺：CPU、内存、磁盘、网络、GPU（NVIDIA） |
| D3 | 管理员路径未验证 | M1 开工前，在一台能点 UAC 的机器上补测 S1/S3；不通过则 LHM Provider 降级为"仅 GPU 用 NVML，CPU 温度延后" |

**已确认成立的技术判断**：NVML 路线、PDH/NtQuery 路线、WPF 自绘性能、PawnIO 随 LHM 0.9.6 提供。

**已被证伪/需修正的判断**：
1. NVMe 温度"零权限可读" —— 至少本机不成立。
2. WPF 下 60 MB 工作集 —— 不成立。
3. LHM 读不到时返回 null —— 不成立（返回 0.0）。
